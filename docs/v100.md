# One Tesla V100 32GB

This is a CUDA execution port of the existing experimental v2 model, not a new
architecture. D=512, depth=8 (shared block), H=8, Q=768, RoPE=384, MHAR=8,
delta wide-state, tied embeddings and per-neuron retention remain unchanged:
**22,043,648 parameters**. CQ is still FP32 and separate at every recurrent
depth. TBPTT remains two 256-token chunks, with independent document masks and
per-row offsets. No datasets or tokenizer need rebuilding.

## Requirements and transfer

Copy source, Cargo.lock, configs, scripts, `artifacts/tokenizer-v2-24576.json`
and the complete `datasets/packed/rx6700-v2-24576` directory. No old `target`,
virtualenv or run/checkpoint directory is required for a fresh run.

Use a Rust toolchain supporting this locked project and **CUDA Toolkit 12.9**,
including NVRTC and headers, with a driver supporting V100 and that toolkit.
`nvcc --version` must report 12.9; the `CUDA Version` displayed by `nvidia-smi`
is the driver's capability, not the installed toolkit version. Select the
matching toolkit libraries in the dynamic loader path as well as its bin in
PATH. CUDA 13 removed offline compilation/library support for Volta; do not
choose it simply because it is newer.
[NVIDIA release notes](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-toolkit-release-notes/index.html).

## First command on the V100

From the project root:

```bash
python3 scripts/benchmark_v100.py --device 0
```

Only Python's standard library is used. This checks that GPU 0 is an idle V100
32GB, checks CUDA 12.9, runs three explicit CUDA smoke tests in each precision
build, then compares FP32 and experimental FP16 projections at B4x16, B8x8,
B16x4. All have **16,384 tokens/update** and the same model, seed and total
schedule. Each case starts from scratch, runs 24 additional optimizer updates
(393,216 tokens, possibly rounded forward to a safe work-block boundary),
and saves its own final checkpoint. Throughput is logged every four updates;
the first interval (four updates) is omitted from the median. No production
training is started. This logging cadence is identical across sweep cases but
more frequent than production, so absolute production throughput may differ.

Results live in a new `runs/v100-benchmark-<timestamp>` directory: `results.json`,
per-case console logs, NVIDIA utilization/power/clocks/temperature/memory CSVs,
generated configs, frozen execution modes and checkpoints. These are retained
for inspection, not automatically deleted; allow several GB of disk space.
The script prints completed cases; while a case runs, follow its `.log` file.
An unsuccessful case cannot win the comparison, and larger batches in its
precision mode are skipped after a failure. `--smoke-only` omits the sweep.

Duration is not yet measured on V100. The six cases process about 2.36M tokens:
at 3,000 tok/s this is ~13 minutes of training, at 6,000 ~7 minutes, **plus**
first compilation, autotuning, smoke tests and checkpoint serialization.
Use measured numbers, not theoretical TFLOPS, for a full-run estimate.

Benchmark-only overrides enable CQ read/write immediately so the sweep measures
the expensive stateful path. Production retains the existing 10M threshold
and 20M read ramp; the speed sweep is not a curriculum experiment. A new fixed
schedule rounding multiple of 16 permits all three physical batches without
changing the comparison's source-tail rounding. Different batch lane layouts
still change context grouping: they are not bitwise-identical trajectories.

## Precision modes and limitations

### Equal-token learning pilots at measured fastest batches

```bash
python3 scripts/pilot_v100_sizes.py --device 0
```

Runs fresh FP32 models sequentially: D512/B8, D640/B8, D768/B8, D1024/B4,
using the fastest completed batches from the user's V100 capacity sweep.
Widths, Q/D and half-Q RoPE match that sweep. Each gets **3072 updates =
50,331,648 tokens**, effective batch 64, with validation/checkpoint requests
every 256 updates (4,194,304 tokens). The final step includes validation.
Validation uses the same 384 single-lane chunks (128 per source) for every
model, independent of training batch; both memoryless and stateful losses and
per-source BPB are retained. D768/B8 was close to the VRAM limit: validation
uses B1 but the complete train/validation cycle still needs a target run.
An OOM is not silently retried with a different batch.

CQ is active with full read scale from the first token, as in the capacity
benchmark. All models keep the same base optimizer/LR schedule, including
10M LR warm-up and the full production decay horizon: this is a prefix
comparison, not four separately tuned or fully annealed training runs.
No production files are modified, and no size-benchmark weights are resumed.
A single seed and differing lane layouts limit conclusions; this experiment
compares the common recipe, not each size's best possible convergence.

At measured speeds 4980/3788.5/2908/1744 tok/s the total is approximately
**19.4 hours of training**, plus initialization, validation and checkpoint I/O.
Allow several additional GB of disk space for the four retained runs.
For a shorter exploratory comparison use `--updates 1280` (20,971,520 tokens
each, about 8.1 hours before overhead); it is too early to conclude final quality.
`--dry-run` generates configs without GPU access or compilation.

Outputs are under a unique `runs/v100-size-pilots-<timestamp>` directory:
`summary.md`, `results.json`, `validation.csv`, per-case console logs and
`train.jsonl` files/checkpoints. CSV records validation loss versus tokens and
wall seconds since each process started, including initialization, validation
and preceding saves. Compare equal-token losses and first crossings of the
same loss threshold to distinguish token efficiency from wall-time efficiency.
Console loss values in CSV are rounded; full precision is in `train.jsonl`.

To stop the whole sequence gracefully, create `STOP` in that timestamped
parent directory. It is forwarded on the next console line to the active run;
the sequence will not launch another model. A failure or early stop also stops
the sequence and cannot be selected as a completed winner. New invocations
start new comparisons rather than implicitly resuming a partial experiment.

### FP32 parameter/capacity sweep

On an **idle V100**, run from the project root:

```bash
python3 scripts/benchmark_v100_sizes.py --device 0
```

This separate harness searches the largest successful physical batch for each
width, not the fastest batch. It uses FP32 only: the earlier experimental FP16
projection benchmark produced a NaN and is not used for this comparison.

| D | Q per head | H*Q | RoPE=Q/2 | Expected parameters |
|---|---|---|---|---|
| 512 | 768 | 6144 | 384 | 22,043,648 |
| 640 | 960 | 7680 | 480 | 30,503,680 |
| 768 | 1152 | 9216 | 576 | 40,143,360 |
| 1024 | 1536 | 12288 | 768 | 62,961,664 |

Counts assume the supplied v2 configuration and vocabulary: `V*D + 3*D*(H*Q)
+ D*H + 3*(H*Q) + 2*D`. Actual counts are parsed from the executable's log.
Depth=8 with one shared block, H=8, MHAR=8, tied embeddings, delta state, gates,
CQ retention, normalization and TBPTT=2 remain unchanged. Width ratios are
preserved; this does not silently add layers or change attention algorithms.

For each width, test B=1,2,4,8,16,32 in increasing order, stopping that width at
the first failure. Accumulation is `64/B`, so each update still consumes 16,384
tokens. B=64 is incompatible with two-chunk TBPTT at this effective batch.
Thus this finds the maximum **supported batch in the fixed-budget experiment**,
not an arbitrary integer VRAM limit (e.g. B=11). A NaN, timeout or other failure
does not establish a VRAM limit; inspect the reported failure classification.
The largest fitting batch also need not be the fastest: all successful speeds
are retained. Batch changes alter stream lane grouping; use equal-batch rows
to isolate width cost.

Each case starts fresh with CQ fully enabled, runs 24 updates / 393,216 tokens,
and excludes the first 8 updates from median throughput. Source budgets, seed,
optimizer and sequence length stay fixed; schedule rounding is 32 for every
case. No production checkpoint is loaded or production config modified.
This measures performance, **not time to reach a target validation loss**.

Outputs: `runs/v100-sizes-<timestamp>/summary.md`, `results.json`, generated
configs, per-case logs, 1-second NVIDIA telemetry and final checkpoints.
Peak VRAM is sampled total device usage, so very brief peaks can be missed.
Failed cases cannot contribute an eligible speed. The default 900-second
per-case timeout kills only the disposable benchmark child; that case may lack
a checkpoint. Ctrl-C cancels the harness rather than starting another case.
Retain several GB of free disk space; output directories are never overwritten.

There are at most 24 cases (9.44M tokens); capacity failures usually reduce that
number. At 1,000–5,000 tok/s the full token budget would take about 31–157
minutes, plus builds, CUDA smoke tests, autotuning and saves. Each case is
bounded to 15 minutes by default; this is not a promise of those speeds.

```bash
# Inspect configs without CUDA, compilation or training:
python3 scripts/benchmark_v100_sizes.py --dry-run
# Longer measurement once the interesting widths/batches are known:
python3 scripts/benchmark_v100_sizes.py --dims 512 768 --batches 4 8 16 --updates 64 --timeout-seconds 1800
```

Passing a short capacity test does not guarantee long-run memory stability or
room for production validation. Leave VRAM headroom and inspect telemetry
before selecting the largest successful batch for an overnight run.

| Build feature | Large projection forward | Backward, master weights, Adam, CQ |
|---|---|---|
| `cuda` | FP32 | FP32 |
| `cuda-fp16` | FP16 inputs, FP32 output | FP32 |

The opt-in mode targets `to_qk`, grouped `proj_up`, delta `proj_out`, and vocabulary
projection. It does **not** cast unnormalized QK, attention-value products, CQ
writes/reads, normalization, gates or wide-state to half. Its custom derivative
uses original FP32 operands (a straight-through approximation to forward
rounding). Even tiny gradients stay FP32, so this mode does not need loss
scaling. It is intentionally **not full AMP** and does not accelerate backward
GEMMs with Tensor Cores. Casting traffic may outweigh forward acceleration.

Do not advertise this as maximum V100 throughput or as numerically equivalent
to FP32. CUDA compilation checks on AMD cannot prove Volta kernel execution,
Tensor Core utilization, sustained memory use or convergence. The GPU smoke
includes a product of 160,000 (larger than FP16's finite range), small-gradient
checks, and a two-chunk all-v2 forward/backward. Passing it only qualifies a
build for benchmarking. Before a long run, compare validation over a longer
matched-token pilot and inspect NVIDIA telemetry/profiler results. A speed
win on 24 updates is not a quality verdict.

Full FP16 backward with FP32 accumulation, dynamic loss scaling and overflow
retry remains future work **after target profiling**; it is not silently
enabled. NVIDIA's general mixed-precision guidance explains why master weights
and treatment of small gradients matter:
[mixed-precision training](https://docs.nvidia.com/deeplearning/performance/mixed-precision-training/index.html).

Both CUDA paths keep Fusion disabled. CUDA reuses allocator buffers between
updates instead of inheriting the AMD-specific forced cleanup every update.
Explicit cleanup around validation/checkpoint/end/error boundaries remains.
No BF16/TF32 or Ampere-only attention kernel is requested.

## Start training only after examining the results

The conservative supplied production config uses CUDA FP32 and B4x16:

```bash
CUDARC_CUDA_VERSION=12090 cargo run --release --locked --features cuda --bin train_llm -- --config configs/v100-v2.json --device 0
```

If another batch wins, edit `optimizer.micro_batch_size` and
`gradient_accumulation` **before starting**, keeping their product 64. For the
experimental precision build select `--features cuda-fp16` and a separate
`run_dir`, e.g. `runs/v100-v2-fp16-projections`. Run directories freeze the
backend/precision in `execution-mode.txt`; restarting them with a different
build is rejected rather than silently changing training arithmetic.

`--max-steps N` can bound a trial. Existing STOP/Ctrl-C checkpoint handling is
unchanged. `complete_llm` remains the existing Vulkan utility: this change
selects CUDA for **train_llm**, not all executables. Public generic model callers
now require `ProjectionBackend`; another backend may implement its default
FP32 operation. The extension has no trainable parameters or record fields.
